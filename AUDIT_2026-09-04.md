## 2. Verdict

**This is a strong, unusually disciplined codebase.** The engineering hygiene is well above what the competition requires: every shipped constant is traced to a measurement, negative results are documented and retained rather than buried, and the packaging pipeline is genuinely airtight.

The problems that exist are **not in the algorithm**. They are in the **measurement and failure-reporting layer** — the parts that tell you how well you are doing and warn you when something has gone wrong. Two of them are material:

1. The evaluator the README tells you to run **computes rejection F1 under a convention this repo's own documentation says is wrong**, and sweeps to an oracle threshold. It overstates rejection performance.
2. `register.py` **cannot distinguish "correctly declined 200 pairs" from "catastrophically failed on 200 pairs."** Both exit 0 with a well-formed CSV.

Neither is hard to fix. Both matter more than they look.

## 3. What is solid — do not touch these

These were verified, not assumed:

- **Test suite: 389 tests, all green** on the exact pinned 3.11 environment. This is real coverage of coordinate conventions, label semantics, scale/score semantics, CLI contracts, and early-exit gates.
- **Submission packaging: 10/10.** The ZIP checker extracts to a temp dir and audits *only that extraction* — required paths, a real `torch.load(weights_only=True)`, a genuine `infer.load_model`, `--help` smoke tests, an import-closure network scan, PDF page count, 27/27 pinned requirements. This is better than most production release gates.
- **Adversarial robustness is excellent.** Six scenarios — missing image, truncated PNG, zero-byte PNG, text-file-as-PNG, duplicate `pair_id`, empty/comma-containing/whitespace `pair_id`, alternate column spellings, 64×64 and 1000×200 images. **Every case emitted exactly one well-formed row per input row and exited 0.** The "declining beats disappearing" principle holds under real abuse. CSV quoting of a `a,b` pair_id is correct.
- **Security posture is clean.** Every one of the 15 `torch.load` call sites uses `weights_only=True` (no pickle RCE). No `eval()`, `exec()`, `shell=True`, `os.system`, or `subprocess` anywhere in the shipped path. `scripts/drive_api.py` reads OAuth credentials from environment variables — nothing hardcoded. No network in the entry-point import closure.
- **Fail-closed model loading.** A failed weights load aborts *before* `predictions.csv` exists rather than silently substituting the classical fallback. Correct, and the loud `[FALLBACK]` banner on the opt-in path is the right pattern (see §5.2 — it should be reused).
- **Documentation of measured decisions is genuinely exceptional.** `config.py` and `FAILURE_ANALYSIS.md` record what was tried, what it measured, and why it was rejected — including things that *lost* (fused6, dedup, rank-transform selection, bicubic sub-pixel). This is the single biggest asset in the repo and is worth protecting.

## 4. Problems — ranked

### 4.1 HIGH — `scripts/eval_phase2.py` reports rejection F1 under the wrong polarity

**This is the most consequential finding.**

`scripts/eval_phase2.py:74` computes:

```python
tp = int(((x >= t) & (y == 1)).sum())   # accepted AND present  = "true positive"
```

That is **found-positive** — a present pair correctly accepted counts as the true positive. But `scripts/grade_emulation.py:21` states the rule explicitly:

> rejection F1 (**REJECT-POSITIVE**: a correctly declined absent pair is the true positive) … the official slide statement that "a system that never rejects scores zero" only holds under reject-positive

`scripts/eval_ext.py:255` and `scripts/grade_emulation.py:148` both implement **reject-positive** as their primary branch. `eval_phase2.py` implements only found-positive, with no switch.

**Demonstration.** A degenerate system that never rejects anything, on a set with 49 present / 11 absent:

| convention | F1 |
|---|---|
| found-positive (`eval_phase2.py`) | **0.8991** — rewards doing nothing |
| reject-positive (`grade_emulation.py` rule) | **0.0000** — correctly scores zero |

**Impact on a real measurement.** On my 60-pair set, same predictions, same ground truth:

| | F1 |
|---|---|
| What `eval_phase2.py` printed | **0.969** |
| Reject-positive at the shipped threshold 0.18 | **0.833** |

Compounding this, `eval_phase2.py` **sweeps for the best achievable threshold** ("best F1 @ score>=0.3128") instead of reporting F1 at `SHIPPED_THRESHOLD = 0.18`. So the printed number is optimistic twice over: wrong polarity *and* an oracle threshold the shipped system never uses.

**Why it matters beyond the number:** the README instructs users to run exactly this script (`python scripts/eval_phase2.py data/val_p2`). Anyone sanity-checking the system — including a teammate, or you at 2am before submission — gets a reassuring number that the repo's own rubric implementation disagrees with. This is a plausible contributor to the long-standing "which score do we actually stand behind" confusion.

**Fix:** make `eval_phase2.py` reuse `eval_ext.py`'s `f1_at()` (reject-positive, default), and report at `SHIPPED_THRESHOLD` with the swept value clearly labelled as an upper bound. ~15 lines.

> Caveat stated honestly: I do not have the organizer's rubric document. This finding rests on **the repo's own internal statement** of the convention, where two of three evaluators agree and the third — the one the README advertises — disagrees.

### 4.2 HIGH — `register.py` has no mass-failure guard

A systematic failure is indistinguishable from a confident all-decline. Demonstrated by pointing all 4 pairs at an unreadable file:

```
|  Reported found: 0/4 (0.0%)                                                  |
EXIT=0
pair_id,x,y,theta,scale,found,score
00000,0,0,0,0,0,0.0        ← ×4
```

**Exit code 0. Well-formed CSV. No alarm.** The only signal is per-pair `[warn]` lines on stderr and a found-rate in a cosmetic summary card.

This is reachable by more than bad images. `locate_phase2` accepts `**kw` and forwards it to `locate()`, which takes **no** `**kw`. A single typo'd config keyword raises `TypeError` inside every pair — verified:

```
TypeError -> locate() got an unexpected keyword argument 'subpixel_row'
```

`register.py`'s per-pair `except Exception` catches it, declines the pair, and continues. **One character in a config change silently converts the run into 200 declined rows and still exits 0.**

**Fix:** the codebase already has the right pattern — the unmissable `[FALLBACK]` banner. Reuse it: track the per-pair exception count and the found rate, and if exceptions exceed (say) 20% of pairs, or the found rate is implausibly low against the ~80% present prior, print an equally loud banner at both the start of the failures and the end of the run. Keep exit 0 and keep writing rows — "declining beats disappearing" is still right — but make it impossible to miss.

### 4.3 MEDIUM — no per-pair timeout enforcement

The 20 s hard timeout is referenced exactly once in the shipped path, at `register.py:596`, as a **post-hoc warning after the whole run has finished**. There is no `signal`, no watchdog, no deadline, no budget check anywhere in `register.py`, `infer.py`, or `driftsense/`.

If one pair hangs, nothing interrupts it. The harness kills the process, and **that pair plus every subsequent pair is lost** — which is precisely the "missing row scores zero" outcome the module docstring calls non-negotiable.

Measured risk is currently low (worst observed pair: 4.82 s against a 20 s limit), so this is a tail-risk item, not a live fire. But the mitigation is cheap and directly protective — see §7.3.

Related, smaller: `f.flush()` at `register.py:572` sits **inside `if not a.quiet:`**, so `--quiet` silently disables per-pair CSV flushing and weakens crash durability. The graded command doesn't pass `--quiet`, so this is latent, but the coupling is accidental rather than intended.

### 4.4 MEDIUM — runtime headroom is materially thinner than the README's headline

The README leads with **median 1.147 s, p90 1.883 s, max 2.191 s** (4 pinned x86 P-cores). My measurements, idle machine, `--threads 4`, exact pinned deps:

| set | median | p90 | max | >5 s | >20 s |
|---|---:|---:|---:|---:|---:|
| 24 pairs | **2.69 s** | 4.29 s | 4.71 s | 0 | 0 |
| 60 pairs | **3.74 s** | 4.39 s | 4.82 s | 0 | 0 |
| 6 pairs (profiler) | 3.66 s | 4.28 s | 4.29 s | 0 | 0 |

Against the **5 s median budget** that is roughly **1.3–1.9× headroom**, not the ~4.4× the headline implies.

This is not a contradiction of the README — it explicitly warns the sub-2 s median "is a property of the faster core, not of the code," and its own E-core row (2.859 s) and `FAILURE_ANALYSIS.md`'s Ryzen row (2.66 s) both land in my measured range. **Two independent measurements and mine now agree at ~2.7–3.7 s; only the pinned-P-core row says 1.147 s.** The headline is the outlier, and it is the number the deck and README lead with.

I also reproduced the repo's own load-sensitivity warning by accident: running the 60-pair eval *while* a coverage run held cores inflated the median from 3.74 s to 4.24 s and pushed max to 5.32 s. Every timing quoted here is from an otherwise-idle machine.

**Consequence:** the earlier guidance in this project that there is "4× headroom" is too optimistic. Plan against ~3.7 s median on unremarkable x86.

### 4.6 LOW — `eval_phase2.py` is not pinned to the shipped config

`register.py` and `scripts/eval_ext.py` both import `SHIPPED_BAND` / `SHIPPED_VERIFICATION` / `SHIPPED_SUBPIXEL_ROWS` from `driftsense.config`, and `tests/test_submission_parity.py` pins them together. `scripts/eval_phase2.py` calls:

```python
res = locate_phase2(model, ref, sea, device, refine=True)
```

— relying on the *function defaults*. Those defaults (`band=False`, `verification="zncc"`, `subpixel_rows=True`) currently match the `SHIPPED_*` values, so it agrees **by coincidence, not by construction**. Change any `SHIPPED_*` value and this evaluator keeps silently measuring the old decode. The parity test does not cover it.

## 5. Where we lag — measured

Fresh `--phase2` sets, shipped weights, 4 threads. These are randomized-composition sets, **not** the A70/B70/C40/D20 spec composition, so they are directional and not comparable to the README's campaign numbers.

| component | n=24 | n=60 | credit tier boundary | margin |
|---|---:|---:|---|---|
| Localisation credit | 0.910 | **0.890** | 1.0 / 0.8 / 0.6 / 0.4 at ≤1/2/3/5 px | median 0.42–0.44 px |
| ≤1 px rate | 80% | **76%** | — | the tier where points are lost |
| ≤5 px rate | 95% | 94% | — | comfortable |
| Scale credit | 0.858 | **0.841** | 1.0 at ≤1% | median **0.66%** → **1.5×** |
| Rotation credit | 0.784 | **0.893** | 1.0 at ≤0.25° | median **0.13°** → 1.9× |
| Calibration AUC | 0.989 | 0.989 | — | strong |
| Rejection F1 (reject-positive @ 0.18) | — | **0.833** | +4 bonus gate at 0.90 | **misses on this set** |

**Three things stand out.**

1. **The ≤1 px tier is where localisation points actually go.** ≤5 px is 94% — essentially solved. ≤1 px is 76%. The gap between 0.890 credit and 1.0 is almost entirely pairs landing in the 1–3 px band. This is consistent with `FAILURE_ANALYSIS.md` §1 and is the correct place to keep pushing.

2. **Scale is the tighter of the two pose components.** Median 0.66% against a 1% full-credit cliff is only a 1.5× margin — a modest degradation on harder blind data moves a lot of pairs from 1.0 to 0.6 credit. Rotation sits at 1.9×. If pose work is prioritised, **scale before rotation**.

3. **Rejection F1 at the shipped threshold missed the 0.90 bonus gate on this draw** (0.833, 11 absent pairs — small sample, one flip moves it a lot). This does *not* contradict the repo's larger-sample numbers, but it is a reminder that the +4 gate is genuinely marginal and that §4.1's inflated reporting makes it look safer than it is.

**Where the time goes** (`profile_pair.py`, 6 pairs, 4 threads):

```
locate (network)     86.1%
pose_candidates      12.2%
polish_pose           0.9%
canonicalize          0.1%
refine_zncc           0.0%
```

The network is essentially the entire cost. This confirms the existing conclusion and reinforces the earlier finding in this project that a Python→C++ rewrite is not worth it: the orchestration layer this would replace is **under 1%** of pair time.

## 7. New ideas

### 7.1 Ship a stripped checkpoint — free 75% size reduction

`weights/driftsense.pt` is 16.50 MB. Broken down:

| key | size | needed at inference? |
|---|---:|---|
| `model` | 4.13 MB | **yes** |
| `raw_model` | 4.13 MB | no — pre-EMA duplicate |
| `optimizer` | 8.22 MB | no — training resume only |
| `arch_kwargs`, `arch`, `epoch`, `best`, … | ~0 MB | `arch_kwargs` yes |

A ship-only checkpoint (`model` + `arch_kwargs`) is **4.13 MB**.

Verified safe: `infer.load_model` reads only `ckpt.get("model", ckpt)` and `ckpt.get("arch_kwargs")`; `check_submission_zip.py` only asserts a `model` key exists; `optimizer`/`raw_model` are consumed solely by `train.py` and `scripts/checkpoint_soup.py`. **There is no weight-hash pin** that a re-save would invalidate.

Best form: strip at *package* time in `build_submission_zip.py`, leaving `weights/driftsense.pt` untouched for training resume. Zero risk to the training lineage, −12.4 MB in the artifact.

### 7.2 Attack the ≤1 px tier, and attack scale before rotation

§5 localises the remaining points precisely: ≤5 px is 94% (solved), ≤1 px is 76% (not). And scale sits at a 1.5× margin from its cliff versus rotation's 1.9×.

The repo already measured that `refit_xy` — re-snapping x,y against the *polished* template — is "the only route by which better pose feeds back into the 40-point metric," and it is **off by default** because it was never A/B'd to a promotion gate. Given that scale is the tighter pose component and the ≤1 px tier is where localisation points live, `refit_xy` is the highest-leverage untested switch already sitting in the codebase. It deserves the full paired A/B before anything new is built.

### 7.3 Budget-aware hypothesis evaluation — buy timeout safety with the 86%

The network is 86% of pair time and is paid **once per pose hypothesis** (3 by default). That gives a natural graceful-degradation lever the code doesn't yet use:

> Track elapsed time inside `locate_phase2`. Before starting hypothesis *k*, if elapsed exceeds a soft budget (say 8 s), stop and return the best candidate so far.

This is strictly better than being killed by the harness: a pair that would have blown the 20 s limit instead returns a possibly-worse answer, and — critically — **every subsequent pair still gets processed**. It reuses the existing early-exit plumbing (`EARLY_EXIT_GATES`, the `break` in the candidate loop), so it is a small, well-understood change. The soft budget should be measured, not guessed, but the current max of 4.82 s means an 8 s budget would fire on essentially nothing today while capping the tail.

### 7.4 Make the found-rate a first-class run assertion

`register.py` already knows `found_count / total_rows`. The composition prior is disclosed (~80% present). A one-line expected-range check in the summary — and in `check_register_contract.py` — turns an implicit sanity signal into an explicit one, and is the cheapest possible guard against §4.2's failure mode.

### 7.5 Reproducibility debt worth clearing

`.agents/PR51_CAMPAIGN.md` justifies several shipped constants but cites two files (`judging/organizer_generator/gen_200.py`, `judging/score_rubric.py`) that are not in the repo. Either vendor them in (they are judging-side tooling, not organizer-confidential data) or annotate the campaign the way `README.md:162` honestly annotates the missing PR #51 generator. Right now a reader cannot reproduce the evidence for constants that are shipping.

### 7.6 Repo weight

115 MB of the repo never reaches the ZIP: `.agents/` 36 MB, `phase1/` 15 MB, unused checkpoints ~48 MB of `weights/` 64 MB. The build allow-list already excludes all of it correctly, so this costs nothing at submission — it is purely clone/CI time. `generator/output/` (33.6 MB of the 50 MB ZIP) is a *required* deliverable and should stay.

## 9. One-line summary

The algorithm and the packaging are in good shape and well-evidenced; **the measurement layer is what needs attention** — one evaluator reports rejection under a convention this repo's own docs call wrong, and the graded entry point cannot tell a triumph from a catastrophe.
